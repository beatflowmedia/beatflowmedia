# 301s for routes removed by the business-model cleanup.
#
# The cleanup dropped the route table from 103 to 58. Only /studio had a redirect;
# the other 47 would have become 404s the moment this deployed.
#
# Per the project SEO standard: a removed URL should 301 to its closest live
# equivalent, never simply 404. /investors is in public/sitemap.xml, so without
# this it shows up in Search Console as "Not found (404)" — a crawl-budget leak
# against a URL Google has already been told to fetch.
#
# 301 (permanent) rather than 302: these pages are not coming back. A 302 tells
# Google to keep the old URL indexed and keep re-crawling it, which is the
# opposite of what is wanted.
#
# Targets are the closest SURVIVING route, not the homepage. A redirect that does
# not move the reader to the next relevant thing is noise to them and dilution to
# the silo — dumping 47 URLs on / would be a worse signal than the 404s.
#

# Netlify takes the FIRST match, and the SPA catch-all at the bottom matches
# everything.

# netlify.toml:123-131 force-redirects an entire SUBDOMAIN at it:
#
#   from = "https://studio.beatflowmediagroup.com"    to = "/studio"
#   from = "https://studio.beatflowmediagroup.com/*"  to = "/studio/:splat"
#
# `path="studio"` no longer exists in AppRoutes.js, so after this deploys every
# request to studio.beatflowmediagroup.com lands on a dead route and falls through
# the SPA catch-all to a blank page. force = true means it happens even for paths
# that would otherwise resolve.
#
# This is not something to guess at — retiring a subdomain has DNS, SEO and
# possibly customer-communication consequences that a redirect file cannot see.
# Three options:
#
#   1. Point the subdomain at the main site:  to = "/"           (or /about)
#   2. Remove the two [[redirects]] blocks and let the subdomain 404 at DNS
#   3. Restore the studio pages, if retiring the portal was not intended
#
# Until one is chosen, the subdomain is broken by this deploy.
